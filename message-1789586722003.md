# NEXS Agent Control Plane — Deep-Research Build Document

I analyzed expert sources on the four hardest parts of this system before writing this plan:

| Concern | Source analyzed | Conclusion adopted |
|---|---|---|
| **MCP lifecycle** | Official MCP spec (2025-06-18), `@modelcontextprotocol/sdk` | MCP servers speak JSON-RPC over **stdio** or **Streamable HTTP**. Lifecycle = `initialize` handshake → capability exchange → `tools/list`, `resources/list`, `prompts/list` → `tools/call`. We wrap this in our own `MCPServerManager`; discovered tools become canonical `Tool` rows. |
| **Durable execution** | Durable-execution-for-agent-runtimes literature (checkpointing, idempotency, replay boundaries, Temporal patterns) | Do **not** call Temporal/Inngest. Build a **DB-backed state machine**: every run/step is a row with status, checkpoint payload, idempotency key, retry count. A worker loop claims queued work, executes one step, persists, commits. Crash → re-claim → resume from last checkpoint. Side effects are recorded in `ToolCall`/`ExecutionReceipt` *before* the step is marked complete, so replay never double-fires effects. |
| **Streaming** | 2026 production guides (SSE vs WS for agent streams) | Consensus: **start with SSE**. It works through any HTTP infra, covers ~90% of agent streaming (the events you listed are all server→client). Upgrade to WebSocket later only if you need mid-stream bidirectional control. So: **SSE** for all `run.* / step.* / chat.* / approval.*` events. |
| **Scheduling** | pg-boss vs BullMQ vs node-cron comparisons | **pg-boss** (Postgres-native, LISTEN/NOTIFY, cron + one-time + delayed jobs, retries, dedupe). No Redis dependency. `node-cron` is in-memory and dies on restart — the spec explicitly forbids that. |
| **Secrets** | AES-256-GCM + KDF best practices | AES-256-GCM with a **master key from env** (`NEXS_MASTER_KEY`, 32 bytes), per-credential random 96-bit nonce, store `v1:base64(nonce):base64(ciphertext+tag)`. Keys referenced by ID, never returned. (Optional upgrade path: HKDF per-tenant key derivation.) |

## 1.3 Technology decisions (locked)

| Area | Choice | Why |
|---|---|---|
| Runtime | Node 20+, TS `strict` everywhere | spec |
| API | Express 5 | spec |
| DB | PostgreSQL 16 + `pgvector` | spec + semantic memory search |
| ORM | Prisma | spec, strong typing |
| Validation | Zod in `@nexs/shared`; `zod` middleware in routes | single source of truth for types |
| Auth | argon2id password hashing; access JWT (15 min) + refresh token (30 d, rotated, stored hashed) in httpOnly `Secure` cookie | standard, simple, revocable |
| Tenancy | `tenantId` on every owned row; single-tenant-per-user at signup (User 1:1 Tenant) but every query goes through a tenant-scoped repository helper | spec: no cross-user leakage |
| Real-time | SSE (`/api/stream?token=…`) | research consensus, §above |
| Jobs/scheduling | pg-boss | Postgres-native durable cron |
| MCP | `@modelcontextprotocol/sdk` Client | official SDK |
| Browser | Playwright (Chromium), one isolated browser context per session | spec |
| Sandbox | in-process Node worker behind `SandboxProvider` interface (child_process, `resourceLimits`, timeout, cwd jail); Docker provider stubbed later | spec |
| Frontend | Vite + React 18 + React Router 6 + TanStack Query 5 + Zustand 4 + Tailwind 4 + shadcn/ui | spec |
| Testing | Vitest + supertest (API), MSW (frontend unit), Playwright (e2e) | spec |
| Lint/format | ESLint + Prettier + `tsc --noEmit` in CI | hygiene |

### 3.1 Vault (build first, everything else depends on it)

```ts
// services/vault/vault.service.ts
const ENC = crypto; // node:crypto
export class VaultService {
  constructor(private masterKey: Buffer) {} // 32 bytes from NEXS_MASTER_KEY
  encrypt(plain: string): string {
    const nonce = ENC.randomBytes(12);
    const cipher = ENC.createCipheriv('aes-256-gcm', this.masterKey, nonce);
    const ct = Buffer.concat([cipher.update(plain, 'utf8'), cipher.final()]);
    const tag = cipher.getAuthTag();
    return `v1:${nonce.toString('base64')}:${Buffer.concat([ct, tag]).toString('base64')}`;
  }
  decrypt(stored: string): string { /* parse v1, createDecipheriv, setAuthTag, throw on mismatch */ }
}
```

### 3.4 Model Gateway (the ONLY door to models)

```ts
// services/models/gateway.service.ts
export class ModelGateway {
  constructor(
    private models: ModelRepository,
    private providers: ProviderRepository,
    private vault: VaultService,
    private adapterRegistry: AdapterRegistry,
    private bus: EventBus,          // emits usage + errors
  ) {}
  async chat(req: { modelId: string; messages: Msg[]; tools?: ToolSchema[];
                    fallbackModelId?: string; timeoutMs?: number;
                    idempotencyKey?: string }): Promise<ChatResult> {
    const model = await this.models.get(req.modelId);
    const provider = await this.providers.get(model.providerId);
    this.assertCapability(model, 'chat');
    const cfg = await this.materializeConfig(provider); // decrypts apiKeyRef
    const adapter = this.adapterRegistry.get(provider.type);
    return withRetryAndTimeout(
      () => adapter.chat(normalizeIn(req), cfg),
      { retries: 2, backoff: 'exponential', timeoutMs: req.timeoutMs ?? 60_000,
        idempotencyKey: req.idempotencyKey },
      async (err) => {
        if (req.fallbackModelId) return this.chat({ ...req, modelId: req.fallbackModelId, fallbackModelId: undefined });
        throw new GatewayError(err); // structured: {code, provider, model, retryable}
      },
    );
  }
  async *streamChat(req: StreamChatReq): AsyncIterable<StreamChunk> { /* same, streaming */ }
}
```

Rules: request/response normalization to a single internal message shape (so Anthropic/OpenAI/Google differences never leak out); usage tracking written to `metadata`/receipts; every failure is a `GatewayError` with a stable `code`.

**Acceptance:** add a provider with a real key → models appear with exact external IDs; `chat` works through the gateway for at least 2 provider types; killing the provider mid-stream produces a structured error + fallback; no code outside `services/models/` imports an adapter.

## PHASE 5 — Execution Engine (Day 9–14) ← *the second heart*

This is where "real execution" is born. Design it exactly like durable-execution systems: **persisted state machine + one-step-at-a-time worker + idempotent side effects**.

### 5.1 State machines

```
Run:    queued → planning → running ⇄ waiting_approval → completed
                        │         │
                        ├─────────┼→ failed
                        └→ paused ⇄ running
                        any → cancelled / timeout

RunStep: pending → running → completed
                     │→ failed (→ retry if under policy → running)
                     │→ waiting_approval → running
                     └→ skipped
```

### 5.2 Engine core

```ts
// services/engine/execution-engine.ts
export class ExecutionEngine {
  // called by: pg-boss worker on job "run.execute"
  async executeRun(runId: string) {
    const run = await this.runs.lockForUpdate(runId);      // SELECT … FOR UPDATE
    if (!isResumable(run.status)) return;
    await this.runs.updateStatus(runId, 'running');
    const checkpoint = run.checkpoint ?? await this.planner.plan(run); // first pass
    while (true) {
      const step = checkpoint.nextStep;
      if (!step) return this.completeRun(runId, checkpoint);
      const stepRow = await this.steps.ensureStep(runId, step); // idempotent
      if (stepRow.status === 'completed') { checkpoint.advance(); continue; } // replay-safe
      await this.steps.setStatus(stepRow.id, 'running');
      this.bus.emit('step.started', { runId, stepId: stepRow.id });
      try {
        const out = await this.executeStep(run, stepRow, step, checkpoint);
        const receipt = await this.receipts.record(runId, stepRow, out);   // side effect LOGGED
        await this.steps.complete(stepRow.id, out);
        await this.checkpoint.save(runId, checkpoint.advance());           // COMMIT boundary
      } catch (err) {
        if (err instanceof ApprovalRequired) return this.pauseForApproval(runId, err);
        await this.retryOrFail(runId, stepRow, err, checkpoint);
      }
    }
  }

  private async executeStep(run, stepRow, step, cp): Promise<StepOutput> {
    switch (step.type) {
      case 'model':      return this.gateway.chat({...});          // via gateway only
      case 'tool':       return this.toolInvoker.invoke(step.config.toolId, step.config.args, ctx);
      case 'mcp':        return this.toolInvoker.invoke(step.config.toolId, ...); // canonical tool
      case 'browser':    return this.browserManager.execute(step.config, ctx);
      case 'sandbox':    return this.sandboxManager.execute(step.config, ctx);
      case 'condition':  return evaluate(step.config.expr, cp.outputs);
      case 'approval':   throw new ApprovalRequired(step.config);   // pauses run
      case 'verification': return this.verifier.run(step.config, cp);
      case 'transform':  return applyTransform(step.config, cp.outputs);
      // …
    }
  }
}
```

Critical properties (each gets a dedicated test):
- **Crash recovery:** kill the worker mid-run → on restart, pg-boss re-delivers → engine reloads `checkpoint` → completed steps are skipped (idempotency key on `RunStep`) → run resumes.
- **Idempotency:** `Run.idempotencyKey` unique → duplicate "start task" requests return the existing run.
- **Timeouts:** per-step `timeoutMs` via `AbortController`; run-level deadline; timeout → `status: timeout` + notification.
- **Pause/resume/cancel:** status transitions + `waiting_approval` handled by the Decision Inbox; cancel sets a flag the loop checks at every step boundary.
- **Concurrency:** per-tenant concurrency limit (e.g., max 5 running runs) enforced by counting `status='running'` before claiming.

### 5.3 Planner (structured, visible plans)

- `planner.plan(run)`: one gateway `chat` call with the agent's instructions + goal/task + available tool schemas, requesting a **strict JSON plan** (`[{id, description, stepType, toolId?, config, dependsOn}]`) validated by zod.
- Store plan in `Run.plan`. Show steps + status in UI. The raw model response is stored in the step's `input/output` (inspectable by owner) but the **plan** — not free-text reasoning — is what the UI renders.

### 5.4 Verifier

`Verifier.run(config, context)` implements: `schema` (zod against output), `http_response` (status/headers/body assertions), `file_exists`, `content` (contains/regex), `tool_result`, `browser_state` (selector/text assertions), `goal_criteria` (evaluates each criterion), `human` (links to Approval). A goal is `completed` **only** when `goal_criteria` verification passes → store `Verification` + `ExecutionReceipt` as completion evidence.

**Acceptance (the "no fake runtime" test):** create a task "use http_request tool to GET example.com, verify status 200" → run it → UI shows real step states, real tool call with real response, verification `passed`, receipt written. Kill the server mid-run, restart, watch it resume and finish.

1. `GET /api/stream` (SSE, JWT via query param or cookie): per-tenant fan-out from the in-process `EventBus`; on connect, replay unread `Notification`s. All emitters (engine, tools, browser, approvals, chat) publish to this one bus → the event catalog from §38 is complete.
2. Frontend `useSSE` hook: reconnect with backoff, dispatch events into TanStack Query cache (`queryClient.setQueryData`) so lists update live without refetch storms.
3. **Dashboard** (`GET /api/dashboard`): one service that composes **real** aggregates — active agents (`status='active'`), running tasks, running workflows, active goals, pending approvals count, recent runs (last 10, live via SSE), recent agent activity (latest RunSteps), provider health (`status` + `lastHealthCheck`), connected services, scheduled tasks (next 5 by `nextFireAt`), recent failures (runs `failed` last 7 d), verification status summary, recent receipts. Quick actions = links to create flows. **Zero hard-coded numbers.**

**Acceptance:** open dashboard + a run detail page in two tabs; start a run; watch both update live without refresh.
