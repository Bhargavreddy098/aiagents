### Design decisions worth remembering
- **Refresh rotation with family revocation.** Every login starts a `family`; each rotation
  extends it. Replaying an already-revoked token revokes the *whole* family (theft detection).
- **Uniqueness is decided by the database, not a pre-flight SELECT** — otherwise two concurrent
  signups both pass the check. `isUniqueViolation(err,'email')` → 409 CONFLICT.
- **Login responses are identical for unknown-email and wrong-password** (same message, and a
  dummy argon2 verify so the timing matches too).
- **Password reset always answers 202**, even for an unknown email (no enumeration oracle).
  Token is claimed with a conditional `updateMany` before the password is written, so a race
  cannot let two requests both succeed.
- **Documented trade-off:** a stateless access JWT stays cryptographically valid after logout
  for up to `ACCESS_TOKEN_TTL_SEC`. Logout/refresh revoke the refresh family, and a password
  change bumps `tokenVersion` (which `createAuthRequired` compares against the row). Flagged to
  the user as an open question — a deny-list would be needed for immediate revocation.

### Tooling hazard discovered (important)
**Never issue two `Edit` calls against the SAME file in one parallel batch.** Each edit reads the
original and writes back, so the last write wins and the earlier edit is silently lost. Three
edits were dropped this way and only surfaced at typecheck. Edits to *different* files in
parallel are fine.

### The fake-db test helper — why it exists
Stubbing the repositories would test nothing, because tenant isolation and rotation live *in* the
repository code. The fake runs the real repositories against real query shapes, so a repository
that changes its query breaks the test loudly. Its `$transaction` callback form snapshots and
restores the tables so rollback is modelled (that is what caught "signup must not leave an orphan
tenant"). The array form cannot roll back — documented inline.

### Real bugs found and fixed (each has a regression test)
1. **`Retry-After` was clamped to `maxMs`.** A provider asking for 30 s was retried after 8 s, earning
   another 429 and burning an attempt. `nextDelay` now returns `retryAfterMs` unclamped; the parser's
   60 s cap is the only ceiling.
2. **`Retry-After` header was discarded** in `openai.ts::post` (placeholder `null`).
3. **A stream that ends without a `finish_reason` was treated as a clean completion.** A truncated
   answer would be persisted and displayed as the model's complete reply. Both adapters now throw
   `ProviderError('unavailable', …truncated)`. Deliberately keyed on `finish_reason` / `stop_reason`
   rather than `[DONE]`, because not every OpenAI-compatible runtime sends the sentinel.
4. **Our own `ApiError`s moved the circuit breaker.** A missing adapter or unreadable credential says
   nothing about provider health. Added `isOwnFault()`; such failures no longer count, and when *every*
   candidate fails that way the specific fault is rethrown instead of `GATEWAY_FALLBACK_EXHAUSTED`.
5. **A disabled model reported "fallback chain exhausted".** An empty candidate list now throws
   `MODEL_UNAVAILABLE` ("disabled, or its provider is disabled").
6. **Anthropic appended `/v1/messages`**, producing `/v1/v1/messages` for any operator who set the base
   URL as the API documents it. Default is now `https://api.anthropic.com/v1`, path `/messages` —
   matching the OpenAI adapter's convention.
7. **`vault.decrypt` rejected its own `encrypt('')`** — the guard was `payload.length <= TAG_BYTES`
   where exactly `TAG_BYTES` is the tag with an empty ciphertext. Now `<`.
8. **`ModelUsage.recent` ordering was non-deterministic** on `createdAt` ties (ms resolution). Added
   `{ id: 'desc' }` as a tie-break so a paginated dashboard list cannot shuffle between reloads.

### Design decisions worth remembering
- **Streaming fallback is refused once content has been emitted.** The plan's acceptance test says
  "kill the primary mid-stream → fallback completes the request"; that is only safe if the primary died
  *before* emitting. Splicing a second model's opening onto a first model's half-sentence produces a
  transcript that never happened. Both cases are tested; the dangerous one throws `PROVIDER_ERROR`.
- **Structured output is resolved per model, not just per provider.** `Model.metadata.structuredOutputMode`
  overrides the adapter default (for a fine-tune that 400s on `response_format`). An override may only
  choose a mechanism the adapter can implement — asking for `json_schema` on Groq is refused, not
  silently ignored.
- **`stream` refuses a requested schema it cannot constrain** (`tool_forcing` needs the arguments
  withheld until the end, which is not a stream) → `UNSUPPORTED_CAPABILITY`, before any request goes out.
- **Gemini has no adapter on purpose.** Its wire shape differs too much; a provider with no adapter gets
  a clear `UNSUPPORTED_CAPABILITY` instead of a mysterious 400.
- **Breaker counts calls, not retry attempts.** Three 503s inside one call's retries = one failure.
- **No in-memory counters anywhere in the model layer.** Every token and cent comes from a `ModelUsage`
  row, so the dashboard number is reproducible with SQL. The acceptance test recomputes the sum by hand.

### Design decisions worth remembering
- **`MCPManager.callTool` never retries on its own.** One attempt, one answer. The only retry is the
  caller opting in via `allowReconnectOnCrash`, and that path refuses with `UNSUPPORTED_CAPABILITY`
  for anything that is not `read_only`. A crashed call is reported with `outcomeUnknown: true` — the
  request was written, so the effect may or may not have landed. This is the phase's acceptance test
  ("no double-fired side effect"), asserted by counting how many times the request reached the wire.
- **Crash teardown is a shared promise.** `onerror` + `onclose` both fire; `settling: Map<serverId,
  Promise>` makes `callTool` await the *same* teardown the transport started rather than racing it.
- **The orphan reaper refuses to kill what it cannot attribute.** A pid is only signalled when
  `/proc/<pid>/cmdline` still shows the recorded command. On macOS/Windows there is no portable
  equivalent, so the row is marked `disconnected` and the pid is logged for a human. Refusing is the
  correct failure mode for an irreversible operation; the normal path (clean SIGTERM → `shutdown()`)
  is what actually guarantees no orphans.
- **MCP annotations are read conservatively.** Only a positive `readOnlyHint` with no contradicting
  `destructiveHint` earns `read_only`; everything else, including an unannotated tool, is assumed
  effectful. Binary content blocks are *described* (mime + size), never inlined as base64.
- **Browser: one Chromium, one `BrowserContext` per session**, actions serialised per session via a
  promise chain (a `click` racing a `goto` fails intermittently, not loudly). The screenshot cap
  degrades full-page → viewport and reports `downscaled`; only if even that exceeds the cap is nothing
  stored, and then the previous ref is deliberately kept rather than pointed at a missing key.
- **Playwright's `Page`/`BrowserContext` are behind structural interfaces** so no test launches
  Chromium — a browser test that hangs leaves a real browser process behind, which is the one thing
  this phase is about avoiding.

### The two remaining engine bugs, fixed
1. **Condition/transform could not see the run input.** `performCondition` built its scope as
   `{ outputs, input: planStep.config['input'] }`, but the run's payload is `run.input`. So
   `left: 'input.go'` resolved to `undefined` for every plan — and because `undefined === 'go'` is
   *also* false, the "condition evaluates false" tests passed **by accident**. Fixed by threading
   `run.input` into both functions and single-sourcing the name space through a new `stepScope()`
   helper, so a condition and a transform can never disagree about what `input` means. A step's own
   `config.input` is now reachable as `stepInput` so it cannot shadow the run's payload.
2. **Approval ids were asymmetric and the emit was unreachable.** The `approval.created` emit sat
   *after* the `deps.approvals === undefined` early return, so with no gate wired no frame was ever
   emitted; and the synthetic id was keyed on the **row** id while `resumeRun`/`resolveApproval` look
   decisions up by **plan-step** id. Fixed by hoisting the emit above the branch and keying the id on
   the plan-step id — which is also the id the outcome hands the caller.

### Three product defects the investigation surfaced (not just test noise)
- **`EmptyPlanError`'s doc comment described behaviour the code did not have** — it claimed "the
  engine turns this into an immediately-completed run" while the engine actually *failed* the run.
  Completing would be the wrong fix (a run that did nothing did not succeed, and `completed` would be
  a status that does not trace to reality), so the comment now states the real behaviour and the
  reasoning.
- **A knowable configuration condition was reported as `INTERNAL`.** `toRunError` mapped everything
  except `PlanValidationError` to `INTERNAL`, so "this agent has no tools" reached the UI as "we have
  a bug". Now mapped to `PLAN_FAILED` — which was declared in the shared error union but had **never
  been emitted by anything**. The message also now names the fix ("grant it at least one enabled tool,
  or supply a preset plan") instead of only stating the problem.
- **The harness's `SeedRunInput.context` was stricter than the runtime.** `Partial<RunContext>` only
  makes *top-level* fields optional, so `limits` still demanded all five values even though the
  resolver merges partials over `DEFAULT_RUN_LIMITS`. Tests wanting to exercise one budget had to
  restate the other four — and so silently stopped testing the defaults. Now

### Follow-up bug: the worker silently exited when the queue was down
Found by actually launching `dist/worker/index.js` — which I had never done.

A worker has no HTTP listener, and in a degraded state no consumer, so it holds **no handle
that keeps Node's event loop alive**. With the queue unreachable it logged `nexs worker
started` and then **exited cleanly** — the worst failure for a background process: a
transient DB restart kills the worker until a human notices, which also undermines the
spec's own crash-recovery test ("kill worker, restart, assert resume").

Fix: `reconnectUntilUp()` retries with exponential backoff (1s→2s→4s→8s→16s→30s cap), and
**the retry timer is deliberately NOT `unref`'d** — while the queue is down that timer is the
only handle keeping the process alive, so unref'ing it would reintroduce the exact bug. Each
failed attempt calls `queue.stop()` first, so a half-open pool is not accumulated. Shutdown
clears the timer so a SIGTERM during a backoff pause is not held for the full delay.

Verified by process observation: ALIVE after 14s and 23s, backoff logged as
2000/4000/8000/16000, with `"queue stopped"` between attempts.

## THE FINDING OF THIS SESSION — a narrowing trap that vitest cannot catch

My post-loop abort check was written as a direct property read:

```ts
for (let round = 0; round <= MAX_TOOL_ROUNDS; round += 1) {
  if (input.signal?.aborted === true) return { interrupted: true };   // pre-round
  for await (const chunk of this.streamOnce(input, messages)) { … }
  if (input.signal?.aborted === true) return { interrupted: true };   // post-round  ← TS2367
```

**The distinction that matters, and that I got wrong the first time:**

- **vitest transpiles; it does not typecheck.** `vitest run` was green (921 passed) with this
  code in place. So was the focused run. A passing test suite is NOT evidence the build works.
- **`tsc --noEmit` (the `typecheck` script) DOES catch it**: `TS2367: This comparison appears to
  be unintentional because the types 'false | undefined' and 'true' have no overlap.`
- **`tsc -p tsconfig.json` — which is the actual `build` script — would have FAILED.** Phase 8
  was one `pnpm build` away from being broken, and every test I had was green.

**Was it a real runtime bug too?** I probed it two ways rather than assuming:
- `transpileModule` on the exact real shape (`for round <= MAX`, inner `for await`, the `if`
  inside a `try`) → the post-round check **is emitted faithfully**. So the *behaviour* was correct.
- So: a **type-check failure only**, not a behaviour failure. The distinction matters because it
  decides the fix — a `@ts-expect-error` would have "worked" and left it unexplained.

**The fix — an accessor the compiler cannot narrow through:**
```ts
function isAborted(signal: AbortSignal | undefined): boolean {
  return signal !== undefined && signal.aborted;
}
```
A function boundary defeats the narrow legitimately (the compiler cannot see through the call),
which is *correct* here because `aborted` really is flipped from another tick — by the abort
listener in `cancel()`. Both call sites now use it; verified both emit (`isAborted` appears twice
in the JS, once pre-round and once post-round).

**Reusable rule:** in an async loop that checks an external mutable flag, never write the
property comparison directly at two points in the same iteration — the first read narrows the
second. Extract a predicate. And never treat a green `vitest run` as "the build is fine": the
gate is `lint` → `typecheck` → `test` → **`build`**, and `typecheck`+`build` are the two that
vitest cannot substitute for.
