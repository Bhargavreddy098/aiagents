# Phase 10, part 2 — `web_search` and the research protocol

The user picked "web_search + protocol" from three options. The reasoning that drove the choice:
Phase 10's acceptance criterion ("research on a real question → ≥3 sources, cited findings, ≥1
verified claim") did not pass, and the spec's own rule is *never start a phase until every
acceptance criterion of the previous phase passes*. So Phase 11 would have been out of order. This
closed the criterion instead.

## What `web_search` actually was

Not "missing from Phase 15" — there is no Phase 15 (corrected earlier today). It is a **spec §3.6
tool-table entry that was simply never implemented**, because a search needs a vendor and none was
ever wired. It is the only entry in that table with no home. Confirmed by grep: no `SearchProvider`,
`brave`, `tavily` or `serpapi` anywhere in `apps/server/src` or `packages/shared/src`, and the spec
does not name a vendor.

## The seam

`apps/server/src/services/search/search-provider.ts` — `SearchPort { name, search(query, opts) }`,
plus a Brave REST adapter over the existing `FetchLike`, plus `createSearchProvider` which returns
**`undefined`** when unconfigured. That `undefined` is load-bearing: `NativeToolRegistry` registers
`web_search` only when a provider object exists, so a deployment with no key never offers the model
a tool that can only fail. A provider named without a key **warns and degrades** to the same place
rather than throwing — search is optional, and refusing to boot an API server over a half-configured
optional integration trades a missing feature for an outage.

Two decisions worth keeping:
- **A non-2xx is an error here, unlike `http_request`.** `http_request` returns a 404 as a *result*
  because its caller is a verifier that must judge the status. Search is different: `{results: []}`
  for a 401 would tell the model the web has nothing to say about the question — a wrong answer
  where a failure was the truth.
- **`external_side_effect`** is the spec's own classification for `web_search` and it is not
  decoration: the query leaves the deployment and reaches a third party.

Config: `SEARCH_PROVIDER` (`none` default) · `SEARCH_API_KEY` · `SEARCH_BASE_URL` ·
`SEARCH_MAX_RESULTS` (5) · `SEARCH_MAX_RESULTS_CEILING` (20) · `SEARCH_TIMEOUT_MS` ·
`SEARCH_MAX_RESPONSE_KB`. The tool does **not** clamp; the adapter does, against the ceiling — one
answer to "how many results is too many", not two.

## The protocol — and why it is a runner, not a preset plan

`apps/server/src/services/research/research.runner.ts`. The obvious design was a preset plan on the
engine run (`RunContext.presetPlan` exists). It does not work, and the reasons are worth recording:

1. The protocol's later stages **write rows** (`ResearchSource`, `ResearchFinding`). There is no
   tool for that, and there should not be — a model-callable "record a finding" would let a model
   invent findings, which is exactly what provenance exists to prevent.
2. A plan is **static**; the protocol is not. "For each search result, read the page" cannot be a
   fixed step list when the result count is unknown until the search runs.

So the protocol is code and `kind` decides the executor in `runtime.ts`. The run is still a real
run row: created, claimed with the same compare-and-swap (`runs.claim`), moved
`queued → running → completed|failed`, completed with the structured result. `ResearchService` owns
the *records*, the runner owns the *work*, and every source/finding is written through the service —
so `recordFinding`'s provenance check cannot be bypassed by whichever component is driving.

Stages, in order, as recorded on `ResearchRun.plan` before the first network call:
`decompose → search → browse → extract → collect_sources → organize_findings → verify_claims →
report`.

## Honesty decisions, spelled out

- **Verification is the `Verifier`'s `content` check**, not a bespoke string compare — the same
  component the engine uses for step verification. The haystack is only the sources the finding
  *cites*, which catches the model that quotes correctly and **attributes wrongly**.
- Both sides are whitespace-collapsed and lowercased first, so the verdict is about evidence rather
  than about line wrapping.
- A claim with **no citation**, or with **no evidence**, is stored `verified: false`. Never true on
  nothing.
- A citation **out of range is dropped, not clamped** — clamping would silently attribute the claim
  to the wrong page.
- Fewer than `RESEARCH_MIN_SOURCES` readable pages → the run **fails**, with the shortfall in
  `result.error` and on the engine run. Reporting a thin answer as `completed` would make the
  status column describe nothing and would hide exactly the case the criterion exists to catch.
- A page that 404s, 403s or yields no extractable text is **skipped and reported in `unreadable`**,
  never recorded as a source. An unciteable source is worse than one fewer: it looks like evidence.
- `startRun` **refuses** (`FEATURE_DISABLED`) when no provider is configured — before creating two
  rows and a queue job. `searchAvailable` is an optional dep, so absent means "do not check" and
  every pre-existing caller and test keeps its behaviour.

## Two real bugs the tests caught

- **`extractText` leaked `<title>` into the body.** The reader stripped `script`/`style`/`noscript`
  but not `<head>`, so every page's body began with its own title — meaning a finding quoting the
  title would "verify" against a string the *reader* synthesised rather than one the page's prose
  contained. Fixed by dropping `<head>` first (`extractTitle` reads the raw document separately, so
  titles still work). Caught by `page-reader.test.ts`, not by review.
- **Four `research.http.test.ts` tests started failing — correctly.** That harness calls
  `createApp`, which builds the **real** container, so `searchAvailable()` was false and `startRun`
  returned 404 `FEATURE_DISABLED`. The tests asserted the old behaviour (a run starts with no
  provider). Fixed by giving the harness a configured provider
  (`loadConfig({...process.env, SEARCH_PROVIDER:'brave', SEARCH_API_KEY:'…'})` — `loadConfig` takes
  an env object) **and** adding a test that asserts the refusal from an unmodified environment. The
  failure was the new gate working.

## Test-harness trap worth remembering

`research.runner.test.ts` had 5 failures that all looked like "findings were not recorded". The
cause was subtler: those tests called `stubThreeSources(h)` (which sets up a corpus keyed by
`'EU AI Act obligations'` / `'AI Act timeline'`) and then **replaced the whole script** with a

that swaps one scripted reply must keep it consistent with the other stubs.**

**The recovery half-story is worth stating precisely.** The engine's crash-recovery *contract* is
real and built: `adoptPriorExecution` (execution-engine.ts:736) adopts a recorded receipt's effect
instead of re-running a step, fails a step whose side-effecting call was recorded but never
confirmed, and re-runs a read-only one. That is what makes re-delivery safe. What is missing is the
thing that *finds* an orphaned `running` run and re-enqueues it — `recovery.scan`. MCP servers and
browser sessions **are** reconciled at boot (`server.ts:90-110`); runs are not. So the engine can
resume a run that someone re-enqueues, and nothing does the re-enqueueing.

**Consequence:** both of Phase 11's acceptance criteria are unreachable today — a schedule cannot
fire (no schedule queue, no `Schedule` repo) and a webhook cannot trigger a workflow (no
`POST /api/events`, no subscription matching). This is a build-out, not a fix.

## Phase 11 (Events & Scheduling) — built out, gate green

The audit above said this was a build-out rather than a fix. It was. What now exists:

**Shared** — `cron.ts` (dependency-free 5-field UTC evaluator: `parseCron` / `isValidCron` /

**Server** — `schedule.repo.ts` + `event.repo.ts`; `ScheduleService`, `EventService`,
`OccurrenceStarter` (the shared "start the run this occurrence calls for", so the idempotency rule

`TaskService.assertTriggerSatisfied` now does **real existence checks** instead of the two
`FEATURE_DISABLED` refusals.

**The design decisions worth remembering:**

- **A queue per schedule means a consumer per schedule.** pg-boss registers crons by queue name, so
  `schedule:<id>` forces its own `work()`, and there is no `unwork`. Hence
  `ensureScheduleConsumers`, called at boot *and* on every recovery sweep, with the sweep interval
  as the documented bound on how late a new schedule's first occurrence can be.
- **The occurrence key is the transport's job id** (`schedule:<id>:<jobId>`), so a redelivery
  collapses into the run it already created while the *next* occurrence still fires. Both halves
  are asserted.
- **The recovery status set is narrower than `listStale`'s default.** `waiting_approval` is
  excluded: a parked run's stale heartbeat is legitimate (a human is the worker), so counting it
  would make the scan's count — the only signal that recovery works — meaningless.
- **`provider.health` probes reachability, not entitlement.** The obvious implementation (a minimal
  completion) spends the tenant's money every ten minutes on a schedule they cannot see. The probe
  is `GET {baseUrl}/models`; the claim made is the claim tested.
- **`recovery.scan` replaces the dead `run.recover` constant** — which had zero usage, like
  `PROVIDER_HEALTH_QUEUE`.

**Two real bugs found by the tests, both fixed:**

1. `ScheduleService.create` did not validate `timezone`. `createScheduleSchema` did, so the HTTP
   boundary was safe — but the service is reachable without the schema, and a stored `Asia/Tokyo`
   with a UTC-computed `nextFireAt` is a **wrong number on screen**. Added `assertUtcTimezone` to
   both `create` and `update`.
2. A one-time schedule's `nextFireAt` after firing was its (now past) `runAt`, so the list endpoint
   showed a spent schedule as permanently overdue. Added `nextFireAfterFiring` → `null` for
   `one_time`.
3. (Third, smaller.) `EventService.ingest` returned the row it read *before* `markProcessed`, so the
   response said `processedAt: null` for an event it had just finished processing.

**The gate caught three dead things the earlier session's notes claimed were clean:**
`cron.ts` had an unused `limit`; `schedule.repo.ts` imported `toJson` without using it;
`control-harness.ts` imported `ScheduleRegistration` without using it. Lint is the step that finds
these and it is worth running first, not last.

### The rule for how a row is written (the useful generalisation)
**Repository when the row has an invariant or an identity a service owns** — agent + version-1
snapshot (`AgentRepository.create`), workflow + version 1 + steps (`WorkflowRepository.create`),
goal completion (`GoalRepository.completeWithVerification`), tool rows derived from the native
registry (`BuiltinToolService.ensure`), credentials (`VaultService.encrypt`), password (`hashPassword`
— the same hasher login verifies against, so the dev account really signs in).
**`db` directly when the row is a timestamped record of something that already happened** — Run,
Step, ToolCall, ExecutionReceipt, Verification, Notification. *Every* repository method that writes
one stamps `new Date()` (`RunRepository.create` hard-codes `status:'queued'`;
`StepRepository.markCompleted` / `VerificationRepository.complete` stamp `completedAt: now`), so a
fixture of the past cannot be produced through them.

### Findings the fixture surfaced (all real, none papered over)
1. **A `sandbox` workflow step is not authorable.** `toPlanStepType('sandbox') === 'tool'`, so the
   step must name a `Tool` row — and the builtin registry registers **no sandbox tool**
   (http_request, calculator, date_time, file_read, file_write, notify, memory_store, memory_search,
   +web_search when a provider exists). The fixture therefore does not author one; authoring it would
   validate and then fail to resolve at run time. **Open gap.**
2. **A `notification` workflow step must carry `toolId`** — `toPlanStepType('notification')` is also
   `'tool'`, because `notify` *is* a registered native tool. Non-obvious; cost a fixture error.
3. **`TaskRepository.update` has no `scheduleId` patch**, so the task↔schedule back-reference
   (`Schedule.targetId` is authoritative, `Task.scheduleId` points back) needs a raw tenant-scoped
   `updateMany`. The two columns also form a genuine cycle: the schedule must be written first.
4. **Connector tools must be registered to exist.** `ConnectorService.registerCapabilities` was
   **private**; made **public** so the seed projects capabilities into `Tool` rows through the same
   code that owns the canonical naming and the capability-asymmetry check. A second copy in a script
   would be a second, weaker opinion about what removes an approval gate.
5. The GitHub adapter's action is **`add_issue_comment`**, not `create_issue_comment`, and the tool
   row's name is **derived** (`canonicalToolName('GitHub','add_issue_comment')` →
   `GitHub__add_issue_comment`). So a step names the *action*; `SeedToolRef` is a discriminated union
   (`builtin` | `connector`) and `run.ts` resolves both to an id.
6. **`AgentContext.allowedToolIds = snapshot.toolIds`** — a connector tool must be in the agent's
   `toolIds`, not just in `connectorAccountIds` (which is stored and mapped but gates nothing).

### Design decisions worth keeping
- **The seed refuses to run twice.** Probe is `users.findByEmail('dev@nexs.local')` — `email` is
  `@unique` **globally**, so it identifies the seeded workspace exactly and needs no new repo method.
  The guard is before the first write; a test asserts the tables are byte-identical after a refused
  second pass (a guard placed after the tenant insert would leave an orphan workspace).
- **MCP server seeded `disconnected`, with no cached tools.** `listAllWithPids` selects `pid: {not:null}`,
  so a seeded `connected` row would survive boot — but nothing would be listening, and a green badge
  over a server that cannot answer is the present-and-broken state the project forbids.
- **Connector seeded `disconnected`** for the same reason, but *with* its capability list: what it
  *can* do is knowable without a working credential, and that distinction is what the row keeps.
  Capabilities are asked of the adapter (`discoverCapabilities` is pure for every implemented
  adapter — no request), so the fixture cannot drift from the adapter's declaration.
- **`running` runs need a fresh `lastHeartbeatAt`** or `RunRepository.listStale` reaps them on the
  first recovery sweep — a fixture that breaks itself on boot. Same for a pending approval's
  `expiresAt` being in the future.
- **`ModelProvider.modelCount` is set from the rows written**, not declared — the honesty rule
  applied to the fixture.

### Test design (`test/seed.test.ts`, 64 tests)
Three kinds: **counts** (what the spec fixes), **invariants** (what the schema encodes but does not
enforce — a completion cites a *passing goal_criteria* verification of the same goal; a receipt for
every executed side-effecting call; a timestamp in every state that implies one), and **traceability**
(every key of `SeedSummary.counts` is compared against the actual row count of its table — the number
the CLI prints is *counted*, not asserted). Also asserts the workflow versions pass
`validateWorkflowSteps` — i.e. the fixture would have been accepted through the API.
Seed once in `beforeAll` with a fixed `now`; only the idempotency tests build their own database.

### Windows gotcha that cost real time

patterns with `NL.join([...])` instead of implicit concatenation, then restore the original line
endings by checking `b'\r\n' in raw`. `container.ts` is already CRLF, so the repo is mixed.

## Session 7 — Phase 14 item 2: crash-recovery, end to end (DONE)

**Item:** spec line 1516, `**crash-recovery** (start run, kill worker, restart, assert resume)` — the
one case in the backend test matrix that was genuinely absent.

**New:** `apps/server/test/crash-recovery.e2e.test.ts` (5 tests). Gate green on the final state:
`LINT=0 TSC=0 BUILD=0 TEST=0`, **73 files / 1523 tests** (was 72/1518 → +1 file, +5 tests), plus a
boot smoke test (`/api/health` 503 `{db:'down',queue:'down'}`, authed route 401, unknown 404).

### The gap: two suites, no seam
Both halves of crash recovery were already tested and each was thorough —
`engine.execution.test.ts` proves the *contract* (a committed step replays from its row, an
interrupted side-effecting call is never repeated, a read-only one is re-run);
`recovery.service.test.ts` proves the *sweep* (`listStale`, the parked/queued exclusions, the
handoff). **Nothing crossed between them.** The sweep emits a `RunQueueJob`; the engine takes
`(tenantId, runId)`. A job carrying the wrong tenant, or a run the engine declines to claim, would
leave both suites green and the run `running` forever. Every test therefore takes the job **from
`harness.enqueued`** and passes its fields — reconstructing it from the test's own knowledge would
assert that the engine can run a run, which was never in doubt.

This is the same shape as the chat double-prefix bug: **two components each tested, the wire
between them never exercised.** Grep for the seam, not for the component.

### Staging a crash without hand-writing the state
A SIGKILL cannot be staged in-process (the DB is in the heap). The technique used: **execute the run
and hold back only the second step.** Run a one-step plan to completion → the run row now holds a
genuine post-step checkpoint (`recordCompletion`'s own output) and a genuine `completed` step row
with a receipt. Then `savePlan` the two-step plan and set the row back to `running` with a stale
heartbeat. Nothing is fabricated but the crash. A hand-written checkpoint would be a second opinion
about the engine's format that agrees with the engine right up until the format changes.

Two windows, because the engine treats them differently: (1) the worker died **after** step one
committed → its row says `completed`; (2) the worker died **during** step two → its row says
`running` and its tool call is `requested` with no receipt.

### What the tests actually pin
- window 1: `pathsReached()` is `['/send','/receipt']` — **one POST and one GET**. A resume that
  re-ran step one reaches `/send` twice; one that skipped step two never reaches `/receipt`.
- the resume **does not re-plan** (`gateway.callCount` stays 1). The stored plan is what runs, and
  a re-planned run would be built by a model that never saw step one's result.
- window 2: the interrupted **read-only** step is re-run, leaving **two** tool-call rows — the
  abandoned `requested` one and the `executed` replacement. Both are honest; collapsing them would
  erase the ambiguity that caused the re-run.
- the job carries the run's tenant, and `executeRun` under the wrong tenant **throws**
  (`does not exist`) rather than silently running the wrong tenant's work.
- a duplicate delivery of a finished run reports `not_claimed` and changes nothing.

### Finding 1 — fixed: a terminal run reported `cancelled`
`ExecutionEngine.executeRun`'s terminal-status pre-check returned `{status:'cancelled'}`, and
`runtime.ts`'s comment directly above the call asserted a completed run comes back `not_claimed`.
**The comment was right and the code was wrong.** `cancelled` is a fact about the *run*; this outcome
describes the *delivery*. The branch now returns `not_claimed`, and the loop's own cancellation
detection still returns `cancelled` for the case that means it. One existing assertion updated
(`engine.execution.test.ts` window 3); the other cancellation test (line ~673) goes through the loop
and is unaffected.

Generalise: **an outcome that answers "what did this delivery do" must not report a fact about the
entity.** Two different questions, and conflating them makes a correct comment look like a lie.

### Finding 2 — REPORTED, NOT FIXED: a duplicate delivery can double-execute a live run
`RunRepository.claim` is a compare-and-swap on **status**, and `running` is in `allowedFrom` — it has
to be, because an orphan's row says `running` and recovery must be able to take it. Consequence: a
claim from `running` **succeeds**, so a second worker handed a duplicate job for a live run claims it
and executes it alongside the first. `recovery.service.ts` claimed the opposite ("a run that is still
genuinely being executed by a live worker **loses the race** and is left alone") — it does not; the
CAS only excludes a claim when the first one *changed* the status.

What actually keeps it rare is upstream: `PgBossRunQueue` sends one job per run
(`singletonKey: runId`) and the sweep only hands back a run whose heartbeat is older than
`RUN_STALE_AFTER_MS`. Both are liveness *heuristics*, so the honest statement is: **a run whose
worker is alive but has not heartbeat inside the window can be executed twice.** The window is
bounded by the longest single step (`ExecutionEngine` heartbeats at every step boundary), not by the
run.

Closing it properly means making the reclaim conditional on the heartbeat that justified it — the
claim does not take one today — and a naive guard (require a stale heartbeat whenever claiming from
`running`) **breaks `resumeRun`**, which sets the status to `running` and then calls `executeRun`
with a fresh heartbeat. So it needs a flag on the queue job or a separate `claimStale` used only by
the recovery path. **Not done in a test phase; both comments corrected to say what the code does.**

### `EmptyPlanError` — a run with no tools and no plan FAILS
`Planner.resolveTools` throws when `allowedToolIds` is empty, *before* asking the model: "the agent
had nothing to plan with" is a configuration to fix, not a run that succeeded at doing nothing. So a
fixture that wants a tool-less run must supply a `presetPlan` (a `transform` step needs no tool).
Cost me one red test — and it is correct behaviour, not a bug.

### Two of my own test bugs, both worth remembering
- `new URL('https://api.test/send').pathname` is `/send`, not `/api/send`. Assert the path, then
  read the path you actually get.
- window 2's fixture writes a `requested` tool-call row and **makes no HTTP call**, so after the
  resume the total is 2, not 3. A fixture that stages a crash *before* the call cannot also produce
  the call's traffic.
