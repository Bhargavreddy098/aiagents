# NEXS — Surfaces build plan (UI/UX v2 §5 and §20)

The Surfaces domain is the eighth subject in this repo: the messaging channels an agent
lives in, the DM pairing queue that lets a stranger in, the devices paired to the gateway,
the routing table that decides which agent answers a surface, and the plugins that can add
any of it. It is the backend half of `v2.md`; the UI half is spec Phase 13 (Frontend).

## S3 — Repositories (remaining)

One file per aggregate, `tenantId` first on every method, `updateMany` + `count === 1` for
every mutation.

- `channel-account.repo.ts`, `access-group.repo.ts` — split out of the channel aggregate so
  each file stays a single cohesive class.
- `pairing.repo.ts` — `findPendingBySender`, `findByCode`, `list`, `countPendingForAccount`,
  `create`, `decide` (CAS on `status:'pending'` **and** `expiresAt > now`), `expireStale`.
- `device.repo.ts` — device CRUD + status CAS, plus `DeviceToken`: `createToken`,
  `findTokenByHash`, `consumeToken` (CAS on `usedAt IS NULL` and `expiresAt > now`),
  `revokeTokensForDevice`, `countActiveTokens`.
- `binding.repo.ts` — `create`, `findById`, `listForResolution(tenantId, keys)` (one
  `findMany` over `matchKey: { in: keys }`), `updateTarget`, `remove`.
- `plugin.repo.ts` — `install`, `list`, `setEnabled`, `findByName`.
- `skill-hub.repo.ts` — the one repository whose methods do **not** take a `tenantId`: the
  catalog is global. Read-only cache; install writes a tenant-owned `Skill`/`SkillVersion`.

## S4 — Services

- **`ChannelService`** — create/update/list/detail; status transitions; account CRUD; the two
  policy invariants: `dmPolicy: 'open'` is refused unless the account's `allowFrom` contains
  `*`, and `deliveryDefault` must name an account that belongs to *this* channel.
- **`PairingService`** — the richest logic in the domain:
  - `request()` generates an 8-char code from `PAIRING_CODE_ALPHABET`, sets
    `expiresAt = now + PAIRING_TTL_MS`, and refuses when the sender already has a pending
    request or the account already holds `PAIRING_MAX_PENDING_PER_ACCOUNT`.
  - `approve()` is CAS, adds the sender to `account.allowFrom`, optionally notifies, and
    optionally makes them the **command owner** — refused with `FORBIDDEN` when an owner
    already exists or the caller lacks `operator.admin`.
  - `dismiss()` writes `dismissed` and **nothing else**: a dismissed sender may ask again,
    which writes a new row rather than reopening this one.
  - `expireStale()` flips overdue pending rows, on the existing pg-boss pattern.
- **`DeviceService`** — `pair()` creates a `pending` device (default `limited`, applied here
  rather than in the schema); `issueSetupCode()` writes a hashed, single-use, 10-minute
  `DeviceToken` and returns `DeviceSetupCode` (the raw token appears exactly once, in the
  response); `approve()` moves `pending → paired` and stamps `scopes` from
  `deviceScopesFor(access)`; `revoke()` sets `revoked` **and** revokes every token;
  `requestUpgrade()` refuses a level equal to the current one and creates a fresh `pending`
  device, so scopes are never widened silently.
- **`BindingService`** — `create()` derives `matchKey` via `bindingMatchKey`, so the unique
  constraint is real; `resolve()` walks `bindingMatchOrder()` and returns the first hit as a
  `BindingResolution` (agent **plus** the winning key, so "Test routing" can explain itself).
- **`PluginService`** — install / enable / disable. A `channel` plugin extends the set of
  channel types `ChannelService` accepts, which is exactly why `Channel.type` is validated in
  the service and not by a schema enum.
- **`SkillHubService`** — cache read + install-from-hub into a real `Skill`/`SkillVersion`.

## S5 — HTTP

Routers `channels`, `pairing`, `devices`, `bindings`, `plugins`, `skills` under `/api/…`,
each built once with the shared `authRequired` and mounted in `http/app.ts`; controllers take
already-wired services from `container.ts`. `nexs pairing list|approve` mutates the same rows
the UI does — one code path, two surfaces.

## S6 — Owner and exec approvals

`Approval.kind = 'exec'` with `requestedAction: ExecRequestedAction` and
`EXEC_DECISION_OPTIONS`. `allow_always` writes a tool allowlist rule; `allow_once` decides one
invocation; only the owner (`operator.admin`) may decide either. This is deliberately a
separate endpoint and schema from tool approvals (§4.4) — one schema accepting both would let
`allow_always` reach a tool approval, where it means nothing.

## S7 — Delivery targets

When a schedule fires, `Schedule.deliveryTarget` resolves to a channel account and the run's
output is posted there. The receipt is written as a `Notification` with
`kind: 'schedule_result'` and a `linkRoute` back into the run — **no new model**, because the
notification vocabulary already carries exactly this meaning and a second table would be a
second place for "was it delivered?" to disagree.

## Decisions locked while building this

- **`Binding.matchKey` is the identity.** A route's parts are all optional, and Postgres
  treats each `NULL` in a unique index as distinct, so a column-wise unique constraint would
  permit two identical catch-all rules and make "most specific wins" undefined. Normalising to
  one non-null key makes the constraint real *and* makes specificity countable (3 > 2 > 1 > 0).
- **There is no `paired → pending` device transition.** Widening scopes is a new pending
  request, so a device can never climb access between two heartbeats without being asked.
- **Scopes are stamped, not read.** A token issued with `operator.admin` keeps meaning that
  even if the device row is later downgraded; the fix for a downgrade is revocation, which is
  visible.
- **Pairing codes exclude `I O 0 1`** — read off one screen, typed into another.
- **`SkillHubEntry` is global.** It is the only non-tenant-scoped table here, and nothing in a
  run ever reads it, so a stale cache cannot affect execution.

## Acceptance tests to write (per step)

1. A duplicate `request()` for the same sender returns the **existing** pending row, not two.
2. The fourth pending request on one account is refused (`PAIRING_MAX_PENDING_PER_ACCOUNT`).
3. An expired request cannot be approved: the CAS matches zero rows and the service says so.
4. `approve({ makeOwner: true })` with an owner already present → `FORBIDDEN`, `madeOwner`
   stays false.
5. A setup token is single-use: the second `consumeToken` fails, and the raw token is never
   readable back from the row (only `tokenHash`).
6. `requestUpgrade({ access: 'full' })` on an already-`full` device is refused, not a no-op.
7. Resolution prefers `telegram|acct|peer` over `telegram|acct|*` over `*|*|*`.
8. Two bindings with the same route produce one row (P2002) — proven, not assumed.
9. Tenant isolation, parametrised over every new `list()`: tenant B sees zero rows of tenant A.
10. `dmPolicy: 'open'` without `*` in `allowFrom` → `VALIDATION_ERROR`.
